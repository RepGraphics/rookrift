# Dokploy: PostgreSQL and Redis

Rookrift 0.10 uses **PostgreSQL 18** as its primary database, suited to Rookrift's relational data and concurrent queries. **Redis 8** optionally caches metric aggregates. PostgreSQL stores all durable application data, including purchase-action jobs; Redis can be restarted or cleared without losing communities, credentials, notes or bans.

The hosted ChatGPT Site remains a browser-local demo. Your Dokploy application runs the live Node/Discord/RCON service and connects to these databases.

## Recommended: Dokploy-managed databases

1. Create a PostgreSQL database service for Rookrift in Dokploy, choose the PostgreSQL 18 image, set a strong password, and deploy it. Use its **internal connection URL** from the same Dokploy network. A separate database/user for Rookrift keeps it independent of other applications.
2. Create a separate Redis service for Rookrift's disposable cache. Use a strong password and its internal URL. Do not reuse Dokploy's own internal Redis service or a queue/session store configured to retain durable state.
3. Create an Application using `RepGraphics/rookrift`, branch `main`, and the repository **Dockerfile**. Set container port **3000** and add the HTTPS domain through Dokploy.
4. Configure the application environment below. Set `APP_URL` and Discord's redirect URI to the actual HTTPS domain. A connection URL's password must be URL-encoded; use the connection URL generated by Dokploy rather than concatenating raw credentials.
5. Use **one application replica** and a **stop-first deployment**. Rookrift's scheduler, Discord gateway and command locks still belong to one runtime. PostgreSQL enforces one active runtime with an advisory lock; an overlapping replacement cannot start until the old runtime stops. If your deployment settings do not expose update order, stop the existing app before deploying its replacement.
6. Deploy. Startup applies versioned PostgreSQL schema migrations. Check `/api/ready` and the application logs, register the bot commands, and exercise one test server.

```dotenv
NODE_ENV=production
PORT=3000
APP_URL=https://your-rookrift-domain.example
TRUST_PROXY_HOPS=1
ENCRYPTION_KEY=your-existing-64-hex-character-key
DATABASE_URL=postgresql://rookrift:URL_ENCODED_PASSWORD@INTERNAL_POSTGRES_HOST:5432/rookrift
PG_POOL_MAX=10
REDIS_URL=redis://:URL_ENCODED_PASSWORD@INTERNAL_REDIS_HOST:6379/0
```

Add the existing Discord and Stripe environment settings from `.env.example`. `ENCRYPTION_KEY` must be the original key when moving existing data. `PG_POOL_MAX` accepts 2–100; the default 10 includes one connection reserved for the runtime lease. Size the PostgreSQL connection budget across your other applications rather than raising it blindly.

Alternatively use standard `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, and `PGPASSWORD` instead of `DATABASE_URL`. The URL takes precedence when supplied. For an external PostgreSQL provider that requires TLS, use its certificate-verified connection settings; do not disable certificate checks. PostgreSQL and Redis ports do not need public exposure when services share an internal network.

Redis is optional: leave `REDIS_URL` empty to query PostgreSQL directly. `REDIS_PASSWORD` can supply the password separately when the URL has no embedded password, as in the bundled Compose stack. A Redis outage degrades the cache while the application continues to use PostgreSQL.

## Redis cache configuration

The recommended Redis instance is cache-only: a bounded memory limit and `allkeys-lru` eviction, with disk snapshots/AOF disabled. No durable data is stored there. For example, a dedicated Dokploy Redis service can use this Run Command:

```text
Command: /bin/sh
Args: -c
Args: exec redis-server --requirepass "$REDIS_PASSWORD" --maxmemory 128mb --maxmemory-policy allkeys-lru --save "" --appendonly no
```

Use this only for the dedicated cache service. Dokploy supplies `REDIS_PASSWORD`; preserve authentication. Do not apply cache eviction/persistence settings to a Redis instance holding another application's jobs, sessions, or other required state.

Only health-chart aggregates are cached, for **15 seconds**, with bounded command waits, a circuit breaker, and coalesced concurrent misses. Cache keys are namespaced by application URL and hashed workspace/server/range identity. Incident notes are fetched fresh. Sessions, team roles/scopes, plan entitlement checks, player notes, ban reports and community sharing preferences are not cached. Permission and opt-out changes continue to take effect on subsequent requests.

## Bundled Compose alternative

`compose.yaml` runs the application, PostgreSQL 18, and Redis 8 together. Fill out `.env`, including `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, the original encryption key, and the application/integration settings. Leave `DATABASE_URL` empty to use the stack's internal PostgreSQL service; Compose supplies its standard `PG*` settings. The application URL remains HTTPS for production.

```text
docker compose up -d --build
```

Only the application binds a host port, on loopback; the databases stay inside the Compose network. PostgreSQL uses the `rookrift-postgres` persistent volume mounted at `/var/lib/postgresql` for the PostgreSQL 18 image. Redis has no durable volume. When deploying this Compose stack through Dokploy, attach the domain to the `rookrift` service at port 3000 using Dokploy's Domains tab. Use its native domain/network handling rather than publishing database ports.

For local backend development only, `compose.dev.yaml` exposes the two databases on loopback:

```text
docker compose -f compose.yaml -f compose.dev.yaml up -d postgres redis
```

Set your local `DATABASE_URL` to the loopback PostgreSQL connection and `REDIS_URL` to the loopback cache URL, then run the existing live backend/frontend development commands. Do not use the development port override in Dokploy.

## Move an existing SQLite installation

The importer supports the SQLite **schema version 4** used by Rookrift 0.5. Upgrade an older installation to 0.5 first. It opens the SQLite file read-only, streams rows in bounded batches, preserves IDs/ciphertexts/timestamps/task ordering, and verifies table counts. The destination must be empty; a failed import rolls back the entire data import. The source is not modified.

1. Stop the old application and take a consistent copy of its SQLite database/WAL files. Retain its encryption key separately. Keep that stopped source as a rollback option.
2. Create a fresh PostgreSQL destination and configure `DATABASE_URL` and the **original** `ENCRYPTION_KEY` in a migration environment. Do not start the new app against it yet.
3. Mount or copy the backed-up SQLite file into the migration environment, then run:

```text
npm run db:migrate
npm run db:import-sqlite -- /path/to/rookrift.sqlite
```

The image also includes the migration command, so an ephemeral container with the same environment and a read-only mount can run:

```text
node scripts/database.mjs import-sqlite /migration/rookrift.sqlite
```

The PostgreSQL runtime lease prevents imports while the new Rookrift runtime is active. Run the import as a separate stopped-app/migration operation rather than a terminal inside an already running application. The importer validates stored encrypted Discord, RCON and hosting credentials using the original key. It refuses populated destinations and never truncates them. If importing fails, fix the reported configuration/data problem and retry against the still-empty destination.

4. Check the verified table counts, start the new application, and verify Discord sign-in, server controls, schedules, team grants, private notes and billing state. Retain the old snapshot until the new deployment has been checked. If rolling back after accepting new writes, reconcile/export those writes before switching back; the original SQLite backup does not contain them.

Existing subscriptions and Stripe price IDs are unchanged by the database move. Redis is not required during migration. `DATABASE_PATH` is no longer used; production startup requires PostgreSQL and does not silently create a new SQLite file.

## Readiness, backups and tests

- `/api/health` reports HTTP process liveness.
- `/api/ready` checks PostgreSQL and returns 503 when it is unavailable; optional cache degradation alone keeps readiness at 200. Responses contain status labels, not connection URLs or credentials.
- Configure PostgreSQL backups and retention through Dokploy, and test a restore. Keep the encryption key separately. Redis does not need a backup because its cache is disposable.
- `npm run db:migrate` is idempotent and uses a migration advisory lock. PostgreSQL migrations live in `server/migrations/` and are tracked in `schema_migrations` independently of the old SQLite version.
- `npm run test:unit` starts isolated Docker PostgreSQL/Redis fixtures automatically, or uses `TEST_DATABASE_URL` and `TEST_REDIS_URL` when provided. Tests create unique PostgreSQL schemas and remove only those schemas. Use a dedicated test database. GitHub CI runs both real services too.

The application uses pooled asynchronous queries, indexed relational reads, connection-bound transactions, workspace row locks for quotas, and batched player snapshots. The external database supports concurrent requests without blocking Node's event loop; it does not by itself make the Discord/scheduler process a multi-replica worker system.
